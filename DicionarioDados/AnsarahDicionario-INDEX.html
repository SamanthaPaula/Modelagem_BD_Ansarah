2. Modelo conceitual e cardinalidades

As cardinalidades descrevem quantas ocorrências de uma entidade podem estar relacionadas às ocorrências de outra. Os pares abaixo são uma proposta de leitura do modelo e devem ser comparados com os símbolos e mínimos/máximos do DER final.

Entidade A Relacionamento Entidade B Cardinalidade sugerida Interpretação
DEPARTAMENTO possui FUNCIONARIO Departamento (0,N) — Funcionário (1,1) Um departamento pode ter vários funcionários; cada funcionário pertence a um departamento.
FUNCIONARIO registra VENDA Funcionário (0,N) — Venda (0,1) Um funcionário registra várias vendas; vendas online podem não ter registro manual de funcionário.
CLIENTE realiza/está associado a VENDA Cliente (0,N) — Venda (0,1) Um cliente pode ter várias vendas; venda de balcão pode permitir cliente não identificado.
VENDA possui ITEM_VENDA Venda (1,N) — Item (1,1) Uma venda concluída contém um ou mais itens; cada item pertence a uma venda.
PRODUTO_SKU aparece em ITEM_VENDA SKU (0,N) — Item (1,1) Um SKU pode aparecer em muitos itens de venda; cada item referencia um SKU.
VENDA possui PAGAMENTO Venda (0,N) — Pagamento (1,1) Permite pagamentos divididos ou pagamento registrado após a criação da venda.
VENDA gera/está associada a PEDIDO_ONLINE Venda (0,1) — Pedido online (1,1) Uma venda pode não ser online; cada pedido online referencia uma venda, conforme o DER.
CLIENTE realiza PEDIDO_ONLINE Cliente (0,N) — Pedido online (1,1) Um cliente pode realizar vários pedidos; cada pedido está associado a um cliente.
PEDIDO_ONLINE possui TROCA_DEVOLUCAO Pedido (0,N) — Ocorrência (1,1) Um pedido pode ter ocorrências de troca/devolução; cada ocorrência mantém o vínculo com o pedido.
FORNECEDOR recebe/fornece para PEDIDO_REPOSICAO Fornecedor (0,N) — Reposição (1,1) Um fornecedor pode atender vários pedidos; cada reposição é destinada a um fornecedor.
PEDIDO_REPOSICAO contém ITEM_REPOSICAO Pedido (1,N) — Item (1,1) Um pedido contém itens; cada item pertence a um pedido.
PRODUTO_SKU aparece em ITEM_REPOSICAO SKU (0,N) — Item (1,1) Um SKU pode ser solicitado em reposições diferentes.
COR caracteriza PRODUTO_SKU Cor (0,N) — SKU (1,1) Uma cor pode estar em muitos SKUs; cada SKU tem a cor definida no modelo.
TAMANHO caracteriza PRODUTO_SKU Tamanho (0,N) — SKU (1,1) Um tamanho pode ser usado por vários SKUs.
MARCA identifica PRODUTO Marca (0,N) — PRODUTO (1,1), Uma marca pode identificar nenhum ou vários produtos, enquanto cada produto está associado a uma única marca.
TABELA_PRECO possui ITEM_TABELA_PRECO Tabela (0,N) — Item (1,1) Uma tabela de preço contém diversos itens; cada item pertence a uma tabela.
PRODUTO_SKU é precificado em ITEM_TABELA_PRECO SKU (0,N) — Item (1,1) Um SKU pode ter preços em tabelas ou canais diferentes.
PRODUTO_SKU possui HISTORICO_PRECO SKU (0,N) — Histórico (1,1) O histórico guarda alterações de preço ao longo do tempo.
TABELA_PRECO contextualiza HISTORICO_PRECO Somente se o vínculo existir no DER Se não houver ligação desenhada, não implementar FK por suposição.
PRODUTO_SKU possui MOVIMENTACAO_ESTOQUE SKU (0,N) — Movimentação (1,1) Um SKU pode ter várias entradas, saídas e ajustes.
FUNCIONARIO registra MOVIMENTACAO_ESTOQUE Funcionário (0,N) — Movimentação (1,1), se ligado no DER Permite rastrear o responsável pela movimentação.
ITEM_REPOSICAO origina MOVIMENTACAO_ESTOQUE Item (0,N) — Movimentação (0,1) Uma entrega parcial pode gerar mais de uma movimentação; ajustes podem ter outra origem.
FORNECEDOR possui CONTA_A_PAGAR Fornecedor (0,N) — Conta (1,1) Um fornecedor pode ter várias obrigações financeiras.
FUNCIONARIO possui conta de acesso USUARIO_SISTEMA Funcionário (0,1) — Usuário (1,1) Um funcionário pode não ter usuário ou ter um; cada usuário pertence a um funcionário.
USUARIO_SISTEMA gera LOG_AUDITORIA Usuário (0,N) — Log (1,1) Um usuário pode gerar vários registros de auditoria.
USUARIO_SISTEMArealizaBACKUP_SISTEMAUsuário (0,N) — Backup (0,1)Um usuário pode iniciar vários backups; cada backup pode estar associado a nenhum usuário, quando automático, ou a um usuário.

3. Fluxo de dados

Fluxo resumido dos principais processos sem introduzir novas entidades.

3.1 Cadastro e variações

Informações de cadastro → MARCA / COR / TAMANHO → PRODUTO_SKU → Estoque e preços

3.2 Venda e pagamento

CLIENTE (quando identificado) → VENDA → ITEM_VENDA + PRODUTO_SKU → PAGAMENTO

3.3 Pedido online e pós-venda

PEDIDO_ONLINE → Separação e despacho → Entrega → TROCA_DEVOLUCAO, se necessário

3.4 Reposição e estoque

FORNECEDOR → PEDIDO_REPOSICAO → ITEM_REPOSICAO → MOVIMENTACAO_ESTOQUE → Saldo atualizado

3.5 Preços

TABELA_PRECO → ITEM_TABELA_PRECO → Preço aplicado → HISTORICO_PRECO

3.6 Contas e auditoria

FORNECEDOR / CONTA_A_PAGAR → Conferência e pagamento → Baixa e consulta

3.7 Backup e restauração

Banco de dados→ Execução automática ou manual do backup→ BACKUP_SISTEMA→ Armazenamento seguro do arquivo
BACKUP_SISTEMA→ Seleção do backup necessário→ REGISTRO_RESTAURACAO→ Execução e registro da restauração

Índices devem ser criados após avaliar as consultas reais. Chaves primárias e restrições UNIQUE normalmente já criam índices próprios no SQL Server.

6.2 Regras de integridade

  • Integridade de entidade: toda tabela deve possuir PK e os identificadores não podem se repetir.
  • Integridade referencial: uma FK deve apontar para registro existente; não criar FK para entidade que não consta no DER.
  • Domínio: quantidades não negativas, preço monetário não negativo e status limitados a valores definidos.
  • Obrigatoriedade: utilizar NOT NULL apenas quando o dado for indispensável ao processo.
  • Integridade temporal: data final não deve ser anterior à data inicial para vigências e períodos.
  • Estoque: impedir saldo negativo se essa for a regra aprovada; registrar ajustes com justificativa.
  • Preços: manter preço aplicado no item da venda e histórico de alterações para preservar o valor praticado.
  • Transações: venda, itens, pagamentos e atualização de estoque devem ser tratados de forma consistente para evitar registros parciais.
  • Exclusão: preferir bloqueio de exclusão de registros referenciados; usar cancelamento/inativação quando for necessário preservar histórico.
  • Backups: manter cópias de segurança e testar periodicamente a restauração.
  • Restaurações: cada registro de restauração deve referenciar um backup existente.
  • Histórico: evitar excluir registros de backup e restauração necessários à rastreabilidade.

7. Logs e auditoria

7.1 Operações recomendadas para auditoria

  • Alteração de preços e vigências.
  • Cancelamento de venda, pedido, troca ou devolução.
  • Ajustes manuais de estoque e correções de inventário.
  • Alterações em cadastro de clientes e fornecedores.
  • Alteração de permissões e bloqueio/desbloqueio de usuários.
  • Operações financeiras relevantes e correções de status.
  • Execução manual de backups.
  • Solicitação e execução de restaurações.

7.2 Conteúdo mínimo do registro

Informação Motivo
Usuário autenticado Atribuir responsabilidade individual.
Data e hora Ordenar eventos e apoiar investigação.
Tipo de operação Distinguir criação, alteração, exclusão lógica, cancelamento e consulta sensível, conforme política.
Entidade e identificador afetados Localizar o registro relacionado sem criar nova entidade de negócio.
Descrição e justificativa Explicar a ação e o motivo quando necessário.
Valores anterior/novo Úteis para mudanças relevantes, evitando cópia excessiva de dados pessoais.

7.3 Controles

  • Não permitir que usuários comuns alterem ou apaguem os próprios logs.
  • Restringir consulta de logs a responsáveis autorizados.
  • Evitar registrar senhas, tokens, dados completos de cartão ou dados pessoais desnecessários.
  • Definir prazo de retenção e descarte conforme necessidade e obrigações legais.
  • Sincronizar relógios e manter cópias de segurança protegidas.
  • Investigar ações atípicas e preservar evidências relevantes.

Proteção de dados pessoais e LGPD

A Lei Geral de Proteção de Dados Pessoais (Lei nº 13.709/2018) estabelece regras para tratamento de dados pessoais. As medidas a seguir são propostas para o projeto acadêmico e não representam certificação ou auditoria da empresa.

Princípios e medidas propostas

  1. Finalidade: usar os dados de clientes e funcionários para objetivos definidos, legítimos e informados.
  2. Necessidade: coletar somente os dados adequados ao cadastro, venda, entrega, atendimento e obrigações legais.
  3. Qualidade: permitir correção de dados incorretos por pessoas autorizadas.
  4. Transparência: informar de forma clara como os dados são utilizados, conforme a operação.
  5. Controle de acesso: limitar CPF, CNPJ, endereço, telefone e e-mail aos perfis que precisem dessas informações.
  6. Autenticação: usar contas individuais, senhas fortes e hash seguro; habilitar autenticação multifator quando disponível.
  7. Mascaramento: ocultar parte do CPF e de outros identificadores em relatórios que não exijam o valor completo.
  8. Logs: registrar operações relevantes sem armazenar senhas, tokens ou dados pessoais excessivos.
  9. Retenção: definir prazos de guarda e descarte considerando obrigações legais, fiscais e necessidades legítimas.
  10. Direitos dos titulares: definir canal e processo para receber e encaminhar solicitações de acesso, correção e demais direitos aplicáveis.
  11. Incidentes: manter procedimento para identificar, avaliar, conter e encaminhar incidentes de segurança.
  12. Backups: proteger cópias de segurança com controle de acesso e testar a restauração.
  13. Compartilhamento: compartilhar dados com transportadoras, prestadores e outros destinatários somente quando necessário e autorizado.
  14. Treinamento: orientar funcionários sobre confidencialidade, phishing, uso de credenciais e tratamento seguro de informações.

Dados pessoais tratados no modelo

Dados Finalidade possível Cuidado recomendado
